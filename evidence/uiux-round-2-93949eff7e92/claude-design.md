## 1. 现状批判（按影响排序）

1. **两条"人"的泳道被拆开了**。现在的列顺序是 决定 | 正在跑 | 闲时池 | 验证 | 流水线 | 结束（`overview.tsx:677-731`）。要人处理的两列中间夹着两列机器状态，眼睛得来回跳。这比闲时池本身更伤注意力。
2. **闲时池太重，还把整个看板拉长了**。每行 `PoolRow` 都是完整卡片带按钮，15 行。更糟的是 `.dt-board` 用了 `align-items: stretch`（`client.css:623`），所有列都被拉到约 2000px，连空的流水线列也成了一大块灰框。
3. **列宽分配反了**。`1fr .72fr .8fr 1.1fr .95fr .85fr` 给闲时池的宽度（0.8）比"正在跑"（0.72）还多，而真正要细读的验证卡只有 1.1。
4. **看板从 y≈517 才开始**。标题、计数、搜索框、计费条占了 1080 首屏的一半，在 1920 宽下只能看到每条泳道的头两三张卡。
5. **验证卡的状态标签会误导人**。`VerificationChecks` 把"版本与前置"也标成"已确认"，于是出现"4 已确认"——那是前置条件，不是检查结论。卡里默认展开 3 行、"展开全部 8 项"，在泳道里太长。
6. **验收页没有按四段组织**。四段的标签和解析函数已经存在（`src/core/verification.ts` 的 `VERIFY_LABELS` / `verifyLines`），但 UI 没用。最该醒目的"待你判断"被埋在第四行；复现用例和工单之间完全没有关联。
7. **代码里有一个会被拖拽放大的坑**。`PromoteRequest` 接受任意 P0–P3，而 `promote()` 不管什么级别都会起一轮新的执行。拖拽一旦做降级，降到 P2/P3 反而会让工单立即开跑。
8. **编辑器页没有给人用的构建入口**。调度器的 `submit` 必须带 ticketId，宿主 job 只能由 worker 排队。

## 2. 方案 A：闲时池改成右侧抽屉 + 拖拽定级（推荐）

**布局**
- 看板改为五泳道：**待你决定 | 待你验证 | 正在跑 | 流水线 | 最近结束**，人的两列在前，机器的在后。
- 列宽 `1.1fr 1.3fr .8fr .9fr .75fr`，`min-width` 改为 960，`align-items: start`，每列最多显示一屏高，超出在列内滚动。
- 泳道上方放一个闲时池入口 `IdleDock`：一枚灰色 chip，写「闲时池 15 · P2 12 · P3 3」，它是唯一的入口。
- 点开后从右侧滑出 `IdleDrawer`，宽 380px，**非模态**，看板仍可操作。打开状态写进 URL 参数 `?idle=1`。

**行的样式（`IdlePoolRow`）**
- 单行标题（不折行）+ 灰色 P 级小字 + 类型 + 等了多久，不显示摘要。
- 拖动把手和 `⋯` 菜单只在悬停或键盘聚焦时出现。
- 默认显示 P2 前 8 行，加一行"其余 N 条"；P3 单独一节，默认折叠。

**拖拽**
- 开始拖动后，看板顶部浮出一条 drop band `.dt-dropband`，盖在泳道头上：**P0 紧急**（红）、**P1 主线**（橙）。放下 = promote，并立即开跑。
- 抽屉内的 P2 / P3 两节本身也是落点：放下只改级别，不开跑。
- 落点高亮用 `data-over`；放到落点以外或按 Esc 取消，行回弹到原位。
- 放下后先乐观移动；接口失败就回弹，并用 toast 显示服务端原话（例如"工单已结束"）。
- 用 pointer events 实现，不用 HTML5 原生拖拽：`pointerdown` 后移动超过 4px 或长按 200ms 才算拖动，期间调用 `setPointerCapture`。Mac 三指拖动在系统层就是按住移动，天然可用。拖动中关掉看板的横向滚动，靠近边缘时自动滚动。
- **拖拽只是增强**。`⋯` 菜单和键盘提供同样的四个级别；拖到 P0 要二次确认（P0 只能由人指定，并且永不自动降级）。

**服务端最小改动**
- 新增 `POST tickets/:id/priority`，只调用 `decidePriority`，不开跑。
- `promote` 收紧为只接受 P0/P1。

**文档**
- 005：泳道表与 Agent status 一行改为五泳道 + 闲时池抽屉。
- 019 §5：改写"提到注意力池"的描述，并补上"拖到 P2/P3 只改级别、不开跑"。

**为什么不选另外两个方案**
- **底部条**：会和计费条、页面滚动抢位置，而且横向条放不下 15 个标题。
- **保留一条窄泳道**：仍然占着首屏的一列，不能根治"分散注意力"。

## 3. 方案 B：验收页 + 一键复现

**`VerificationGate` 的信息层级**（从上到下）
1. **判断条 `.dt-verify-judge`**，滚动时吸顶：「待你判断」的内容加粗显示，右侧放「本地验证通过」（主按钮）和「退回」。
2. **复现区 `ReproInline`**：先列「复现步骤」，再放关联到的用例卡，带 [运行] 按钮、实时输出（最近 40 行）、[打开报告] 和 [在编辑器页打开]（`editor?case=<id>` 锚点）。
3. **证据**：「预期与证据」默认展开，日志和报告路径做成可点击链接。
4. **前置**：「版本与前置」做成键值列表（CL / review / 构建 / 工作区），不加状态标签。
5. 文件清单、原文、Session 链接收进折叠区。

四段统一用 `verifyLines` 解析；解析不出四段时，退回现在的 `VerificationChecks` 显示。

**通过按钮的禁用条件**
- 已有交付依据（现有的 `hasBasis` 判断）**或**关联到了用例，才显示「通过」。
- 用例正在运行时禁用，提示"等这次复现跑完"。
- 最近一次运行失败时不禁用，但确认框要写明"最近一次复现失败"。

**工单与用例怎么关联**（在客户端完成，零接口变更）
- 优先级 1：验证文本里出现了用例的文件夹名（真实数据就是这样，例如 `…_ZZAttack05`）。
- 优先级 2：文件夹名里包含工单 id 的前 8 位（你给的例子 `20261105-183235-c75bbc4c_…` 看起来就是这个命名习惯）。
- 匹配逻辑写成纯函数，放在 `src/core/verification.ts`，前后端都能复用。

**`case.json` 本轮不加工单字段**。它的校验是 `.strict()`，旧宿主读到新字段会把整个用例判为非法。等以后要加时，应先放宽校验、晚一个版本再写入字段，并更新 docs/024。

**找不到用例时**：显示"这次交付没有可运行的复现用例"，下面附 worker 写的复现步骤原文，再给一个按钮「让 worker 补用例」——本质是一次退回，退回说明预先填好。

**"一键"的边界要说清楚**：它等于运行 `case.json` 里的命令。临时应用测试文件、构建、跑完再 revert，这些都必须由 worker 写进用例命令里，面板不会替人重放"版本与前置"。可以在工作指令（`prompts/work.md`）里要求用例自包含。另外，现有逻辑是 agent 或宿主 job 占着编辑器时不让人跑用例，这时按钮禁用并显示占用者，同时给出"抢回编辑器"入口。

**串成一个宿主 job**：新增人触发的 job，类型 `buildLaunch`，执行 `Build.bat <Target> Win64 <Config> -Project=… -WaitMutex`，成功后再启动编辑器或游戏。

## 6. 风险清单

- **接口契约**：`promote` 收紧级别可能影响飞书或其他调用方，要先全仓 grep；新增的 `priority` 接口要在 `api.ts` 和 007 的 HTTP 表里登记。
- **兼容**：`case.json` 是 `.strict()`（见上）；抽屉状态只放 URL，不持久化。
- **多语言**：新增的 `idleDrawer*`、`dropP0` 等文案中英文都要补，英文较长，抽屉宽度要按 en 测；四段标题本身是中文协议字段，作为数据原样显示，不翻译。
- **暗色主题**：drop band 的颜色用 `color-mix` 配 `--dsw-alias-state-*` 变量，不要写死 `#d4a300`。
- **键盘可达性**：抽屉支持 Esc 关闭、关闭后焦点回到入口 chip；每行可以 Tab 到，`⋯` 菜单支持方向键；落点要有 `aria-live` 播报。
- **触控板 / Mac 三指拖动**：三指拖动在系统层是按住移动，可能触发文字选中，拖动中要设 `user-select: none`；也可能触发横向滚动或系统的返回手势，拖动时要关掉看板的横向滚动；4px 的起拖阈值用来防止误触。
- **测试**：jsdom 不支持 `setPointerCapture`，需要打桩；拖拽建议在本地复现入口跑一遍端到端截图。

**我不同意的一点**：拖拽不该是唯一入口。核心价值来自"抽屉 + 一键定级"；拖拽锦上添花，排在 PR2，不能拖住 PR1。
