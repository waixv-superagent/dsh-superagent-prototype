# 025 — 闲时只读分析：让池子里的票自己证明值得注意力

> 2026-11-06 · 由自动化代理（大肥鱼）实现，依据 11-05 复盘「闲时池最小队列」与「简报不能解决问题」的方向修正。
> 本文说明这一版落地了什么、边界在哪；没做的部分写清楚，不当作已完成。

## 0. 一句话

`P2`/`P3` 的工单在闲时窗口里先跑一次**只读分析**：收集证据、找出同类、给出一个可行动的结论
（`promote` 推进 / `merge` 并入同类 / `archive` 先归档），不改代码、不交付、不自动改优先级；
分析完成后这张票停在池子里等人按结论处理，闲时门不会自己再跑一遍。

## 1. 为什么不是「早上给一份简报」

11-05 的方向讨论里，人对第一版「早上简报」的判断是：**简报不能解决问题**。看板池子里摆出来的东西
必须都是值得花注意力的；真正占机器资源的执行器必须是在推进的重要任务；人随时能把池子里的票挑进
注意力池。简报只是又一层要读的文字，没有改变「池子里什么都有」这件事。

这一版把输出从「写给人的简报」改成**写在票上的结论**：一张票在池子里值不值得看，由它自己的分析结论
回答，看板/卡片直接读这个结论；不需要人先读完一段摘要再判断。分析本身也不产生交付，只把下一步需要
人做的决定压缩成一句话。

## 2. 一次闲时分析

启动门仍是 [019 优先级与闲时](019-priority-and-idle.md) 的五信号三层（`L1`/`L2`/`L3`），但
`executor.idle.analysis.enabled`（默认开）让 `P2`/`P3` 的闲时启动改跑分析，而不是实现：

| 之前 | 现在（默认） |
| --- | --- |
| `P2`/`P3` 在闲时窗口里直接实现，可能改代码、开 PR/CL | 第一次闲时启动跑只读分析；结论等人处理 |
| 分析完成后没有状态，下一轮还会再启动 | `idle.analysis.state = ready` 后闲时门挂起：只有人的消息/提级才继续 |
| 没有结论载体 | 工单上记 `idle.analysis.advice`，卡片/看板行带 `analysis` |

一次分析的完整状态：

```
（进池）→ running →（报告 ready）→ ready  → 人等结论（提级、并入、归档）
                 ↘（报告 blocked/failed/dropped）→ failed → 人决定是否再跑
```

- **只读**：worker 的 `write`/`edit` 工具被拒，`orchestrator_plan`/`orchestrator_phase` 被拒，
  会改工作区的 shell 命令被拒（与 P1 方案门同一套命令黑名单）；系统提示追加 `## idle analysis`
  一节，说明交付指令（PR/CL/方案卡）在这一轮不适用。这是一层**阻断而非沙箱**：黑名单之外的自定义
  脚本仍可能在磁盘上写东西，分析指令明确禁止，且不产生交付，所以不会被当成实现。
- **读什么**：工单来源消息、线程、代码、已有报告与复现用例；不为了填满章节去启动编辑器或长任务。
- **同类**：启动时用关系图的确定性相似猜测（`views/similar.ts`）挑最多 `analysis.related` 张
  「可能同因」的票写进 brief；worker 可以核对，并在结论的 `同类` 一节里点名。猜测永远不是已记录关系，
  也不替人做决定。
- **结论**：结论随报告一起交：`orchestrator_report` 的 `ready` 把 `summary` 当研究稿、把 `sections` 当结论
  （`结论` = promote|merge|archive，`理由` = 一句话，`同类` = 重复票 id，`代价` = 推进要花什么）。引擎把
  结论存成 `{ verdict, reason, merge_with?, cost? }`，并把 `同类` 里不存在的 id 直接拒掉；`cost` 让注意力可以按代价权衡。
- **正文**：`orchestrator_report ready` 的 summary 就是研究稿，固定六节：
  现象 / 证据 / 复现 / 同类与框架 / 建议动作 / 代价与风险，约 1200 字以内。报告 ready **不会**
  结束工单、不会开本地验证门、不会唤醒主会话或发卡片；静默是设计的一部分。
- **失败**：`blocked`/`failed`/`dropped` 记为 `failed`，同样不自动重跑；`progress` 保持 running。

## 3. 谁能让它继续

- **人提级**（线程里回 `p1`、点优先级卡）：离开闲时池，下一次启动就是普通实现。
- **人在线程里说话**：`personWaiting` 让闲时门直接放行（这条路径在 019 就有），分析状态不挡人。
- **人回复 `p2`/`p3`**：留在池子里；已完成的结论不会被覆盖，除非再有人在票上说新内容触发新派工。
- **机器人/CI/订阅消息**：不会让它自动实现，也不会重跑分析；`ready`/`failed` 两种状态都挂起。

## 4. 数据与配置

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ticket.idle.analysis.state` | `running \| ready \| failed` | 分析的生命周期 |
| `ticket.idle.analysis.assignmentId` | string | 跑这次分析的派工，结论只认它 |
| `ticket.idle.analysis.level` | `L1 \| L2 \| L3` | 哪个闲时深度放行的 |
| `ticket.idle.analysis.startedAt / endedAt` | ISO 时间 | 起止 |
| `ticket.idle.analysis.advice` | `{ verdict, reason, mergeWith?, cost?, at }` | 结论；`mergeWith` 只接受存在的工单 id、最多 3 张、不含自己 |

全部是可选字段，SQLite schema 不变（仍是 `schema 11`），旧记录无需迁移；旧单没有 `idle`，与新行为无关。

配置在 `executor.idle.analysis`（保存设置即可，默认值即本文档）：

```json
{ "enabled": true, "related": 3 }
```

- `enabled: false` 恢复 019 的行为：`P2`/`P3` 在闲时窗口直接实现，不跑分析。
- `related` 是 brief 里列出的相似票上限（0–3）。

工单卡（`orchestrator_read` 的 ticket card）与看板行多出 `analysis` 字段：
`{ state, verdict?, reason?, label?, cost?, mergeWith?, startedAt, endedAt? }`。
`label` 就是人看的那一句：`值得现在投入注意力` / `并入同类，看代表票` / `先归档，不值得现在看`。

## 5. 明确没做的部分

- **看板 UI/UX 与注意力池**：本文只提供「池子里的票值不值得看」的数据和结论，看板怎么筛选、
  怎么把票挑进注意力池、执行器怎么排序，是注意力分配工作流（另一张单）的事；本单不改面板客户端。
- **跨票的框架重构专题**：一次分析只看自己与最多三张相似票；「三张以上同因」只能在同一张票的分析里点名，
  还没有一个跨池子的批次会话去产出一份全局重构议题；这是 11-05 复盘里「系统考虑框架设计」的下一步。
- **自动提级**：分析结论不会自己把票变成 `P1`；`promote` 只是一个建议，改优先级仍要人。
- **自动跑复现**：复现用例的自动重放属于复现 harness 工作流；分析只写「怎么复现」和已有证据，
  不启动编辑器、不写入 `Saved/ReproTests`。
- **同类归并的落地**：`mergeWith` 只是一组 id 和一个建议，不会自动关闭/合并工单。
- **沙箱级只读**：命令黑名单覆盖仓库/引擎常见写法，不覆盖任意脚本的副作用；没有文件系统层只读挂载。
- **跨夜的进度续跑**：分析走普通派工，宿主重启按 003 恢复；没有单独的「夜间批处理进度」。
- **早间推送**：没有飞书简报/摘要；结论留在票上和看板行里，由人的注意力入口读取。
