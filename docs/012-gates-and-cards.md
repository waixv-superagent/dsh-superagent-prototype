# 012 — 分阶段闸口、红线与飞书介入卡片

本文定义从 TAPD 缺陷到 p4 入库这条链上**人在哪里介入**、**哪些规则机器强制**、**介入卡片长什么样**。
它建立在 [001 Domain](001-domain.md)、[002 Authorization](002-authorization.md)、[003 Execution](003-execution.md)、
[009 p4/Swarm](009-p4-swarm.md)、[011 Task center](011-task-center.md) 之上。

## 1. 五个阶段与三个人门

| 阶段 | 谁做 | 人工介入 | 状态 |
| --- | --- | --- | --- |
| P0 接单 | 主会话评估 + 接单规则 | 可选：批量预审 | 已有 allowlist / 评估，无预审 |
| **P1 定位 + 方案** | worker（只读：代码、资产、配置） | **必过门**：交方案，人点选项（默认三项，worker 可改） | 已有（方案卡 + 动态选项） |
| P2 实现 | worker | 不打扰，受预算约束 | 已有 |
| P3 验证 | worker | 机器关卡；失败自动修，超预算才叫人 | 已有（编译 + 自动化测试） |
| **P4 交付确认** | worker | **必过门**：CL + shelve + review + 对比结果 | 已有（`human_action` / attention） |
| **P4.5 本地验收** | **人** | **必过门**：worker 交付 CL / review 后，人本地跑一遍再判通过或退回 | 本轮新增（`ticket.verification`） |
| P5 入库 | **人** | 由人 submit；agent 永远不 submit | 已有（p4 包装拦截） |

P1 是这一轮最贵的教训：一个引擎插件改动、40 分钟编译，在任何人看到之前就发生了。P1 门的存在意义就是把这个成本压到 3 分钟的一句话。

P4 与 P4.5 是两个不同的门，别再混在一起：**P4 确认「可以提交」**（字段 `confirmed`，人自己跑 submit）；**P4.5 确认「我本地真的验过」**（字段 `verification`）。
worker 自验的文本（编译结果、自动化通过数）只是证据，不是验收；过去的看板把它们当成「已完成」，于是 12 张单全是 `humanConfirmed=no` 却看不出区别。

## 2. P1 门的产物（固定模板）

```
现象：<一句话>
代码线：<文件:行> + 证据 ／ 已排除的原因
资产线：<资产路径或配置项> + 证据 ／ 已排除的原因
配置线：<ini／cvar／DataTable 行> + 证据 ／ 已排除的原因
修复锚点：<准备改哪里，几个文件，是否引擎／公共模块>
影响面：<跨模块？动资产？动配置？CL 冲突？>
验证方案：基线跑什么（改前） → 改后跑什么 → 比对什么指标
预算：<预计编译 N 次、总时长>
```

- 三线不是必填三栏，但每一线必须有「已确认 / 已排除 + 依据」。写死成必填会逼出编造，写死成可选就只会看代码那条线。
- 人只回三种：**改** / **换方向（附一句）** / **停**。

## 3. P4 门的产物（固定模板）

- CL 号、shelve 状态、Swarm review 号与链接
- 改动摘要：文件数、是否引擎／公共模块、是否动资产或配置
- **改前 / 改后对比**：基线结果、改后结果、差异结论；没有基线必须写明原因（P4 卡片会标「无对比」）
- 回退方式：CL 号 + p4-iteration git 的 commit（分支名、commit hash）
- 待决点：需要人拍板的具体问题（TAPD 状态、引擎改动、负责人卡点等）

## 3.1 P4.5 本地验收门

P4 之后的交付物**不会自动结束工单**：worker 报 `ready` 且带 changelist 或 review 时，`assignments.report()` 写入
`verification: { at, state: 'pending' }`，同时从这一刻起由**主机侧**跟进 Swarm 流水线（`PipelineWatch`，见 009 第 5 节）；
工单保持 open，阶段先报 `pipeline / running`（绿了待审是 `pipeline / blocked`），人的本地验收 `person / verify` 与流水线并行。
没有交付物的分析单照旧直接结束。git 后端没有流水线，本地验收仍是最后一道门。

字段与流转：

```
ticket.verification = { at, state: 'pending' | 'passed' | 'failed', by?: 'person' | 'pipeline', note?: string }
```

- **通过**：`POST tickets/:id/verify`。p4 单只记 `state: 'passed'` 和 `by: 'person'`，**不结束工单**，因为提交还没发生；
  主机的流水线跟进在 CL 真正提交后才以 `by: 'pipeline'` 结束它。git 单仍在通过时结束。已结束的 completed 单也允许补记
  （历史数据没有这个门），补记只补事实、不改结论。
- **退回**：`POST tickets/:id/rework { note }`。记 `state: 'failed'` 和人的原话，阶段回到 `implement`，结束当前 Assignment，
  新建一个 Assignment，人的原话作为第一条 Input，worker 按它修完再报 `ready`，门重新变 `pending`；重新交付会重置流水线观察。
- **不是 submit**：通过只写 `verification`，不写 `confirmed`、不动 CL；P5 仍由人执行，提交成功由流水线跟进收单。
- **证据留档**：worker 的 `execution.verification` 文本原样保留，在卡片/工单页作为「worker 跑了什么」展示，并与人的结论分色。

看板按这个门重排成四列（左→右）：**待你决定 · 待你验证 · 进行中 · 已结束**。列的顺序就是人该看的顺序；
头部一句「N 件等你验证 · M 件等你决定 · K 件在跑」先给总数。已结束列每张单带验收来源徽标
（`你已验` / `worker 自验` / `未验`），列顶一条「12 张已完成，0 张经你验证」并把「补验」直接链到 `filter=unverified`。
验收门只对 `person / verify` 这一种 stage 出现，不新造一套状态；这与 Orca 把 `permission` 提升到 Done 之上的做法同构。

## 4. 红线：机器强制 vs 人看

| # | 规则 | 强制方式 | 依据 |
| --- | --- | --- | --- |
| 1 | 禁止 `p4 submit` | 机器：worker 的 p4 包装拦截 | 已实测拦截 `p4 submit -c 123456` |
| 2 | TAPD 状态：受理后 agent **可**置为「修复中」；「修复完成」由 Swarm 入库流水线自动流转，agent 不许手动设 | 机器：只允许白名单内的状态迁移 | 用户决定 |
| 3 | **「修复完成」（resolved）的缺陷根本不进流水线**：在 Source 读取阶段就排除，不产生 Trigger、不进评估、不建单 | 机器：`openStatuses` 默认 `new\|in_progress` | 用户纠正（源头错了，不是门的问题） |
| 4 | 一 bug 一 CL；CL 描述中文、只写变更本身 | 机器：shelve 前校验描述 | 保留 |
| 5 | 不动别人／你已有的 pending CL；**除非有关联文件**（同一文件或同一逻辑改动） | 机器：CL 白名单 + 关联文件例外 | 用户修正 |
| 6 | P1 未过门不许写代码；P4 未过门不许 shelve／开 review | 机器：阶段状态机 | 待实现 |
| 7 | 门超时默认「停」，不默认继续 | 机器：默认值 | 待实现 |
| 8 | 改引擎／第三方：不强制用厂商 handle 包裹，但**改引擎必须在 P1 门明示并等人点头** | 人看 + 机器提示 | 用户修正（"只是改引擎应该慎重一点"） |

规则 1、2、4、5 是机器可校验的，写进代码；6、7 是阶段机的一部分；8 靠 P1 门暴露给人判断，不写死。

## 5. p4-iteration git 的提交粒度

- 按**里程碑**提交：定位完成 / 实现完成 / 验证通过 / shelve 前，各一个 commit。
- 不固定死四个：长迭代允许更细（每次有意义的状态变化一个）。
- **人给过反馈或修正之后，必须补一个 commit**，把修正前后的差异留成可回退的点。
- 每个 commit message 带 CL 号与迭代序号，例如 `CL 123456 迭代 3：按反馈改为只对 DS 环境去重`。

## 6. 介入卡片与决策入口

原则来自官方设计哲学「decide inline, evidence spill」：**人只在一处做一次决定，证据按需展开**。人不是执行器，
不要把八行模板原样推到聊天里再让人回数字。

### 6.1 形态：决策简报（Card 2.0）

P1 卡片正面的信息量压到一眼能答：

1. **标题**：`待确认 · 方案已出`，副标题是工单标题；达到 24 小时闸口的那张带 `等你点头` 标签。
2. **颜色**：P1 待批 = 蓝；被卡住 = 红；已结束 = 绿。
3. **现象**一段：说清问题；多个要点自动拆成一行一条。
4. **修复锚点**一段（要改哪里、几个文件、是否动引擎／公共模块；多个要点自动拆成一行一条）。
5. **影响面 · 预算**：一行 `notation` 字号的事实，不展开成长段。
6. **证据折叠**：`collapsible_panel`（默认收起）里放代码线 / 资产线 / 配置线 / 验证方案四条完整依据；正面不重复。
7. **通过后**一行：`通过后` 开始实现、按验证方案验证、再交给人确认交付、不直接 submit；像正常对话里问问题时把下一步说清。
8. **选项按钮**：worker 给的 2–4 个（默认 `通过` primary / `改一下` default / `停` danger 带二次确认），一行排开；`改一下` 带 `note` 时直接记这个方向，没有 `note` 才换成表单。
9. **底部灰字**：`<截止时间> 前不答就自动停`，说明超时默认停，不默认继续。

每个块是**一个加粗小标题 + 一行一条的要点**：正文按 worker 的换行和句号／问号／叹号拆成要点（普通要点前缀 `• `，worker 自带的 `1)`／`1.` 序号写成 `1、`，避免 Feishu 把序号解析成嵌套列表而多出一层缩进），过短的中段尾句并入上一条（上一句以句号结尾时不再加空格），块的最后一句（如「推荐 B。」）单独成行、不加圆点，结论不会被读成上一条的一部分；一条超过一屏再按分号拆。标准布局的八行、worker 自定义的 `sections`、折叠里的证据和文本兜底都用同一套排版，长段不再糊成一堵墙；折叠里只有一块时，块内不再重复折叠标题已经写过的小标题。裸 URL 自动变成可点击的标题（`飞书文档`、`PR #9`、`Jenkins 构建`，未知域名用主机名），worker 自己写好标题和地址的 markdown 链接原样保留，所以人看到的是标题而不是地址；`& | ^ ! % < >` 作为命令行参数时用 JSON unicode 转义（`\u0026` 等），Feishu 解析 JSON 后还原，所以带 `?a=1&b=2`、`%2F` 的 URL 能整条点击跳转，而不是被全角化或截断。

按钮是**真回调**：`behaviors: [{ type: 'callback', value: { v: 1, decision } }]`，点击产生 `card.action.trigger`，
不依赖人在聊天里打字。`改一下` 先把卡片替换成一个带输入框的表单（`form` + `note`），提交时带上那句新方向。
表单不把上下文丢掉：顶部保留原问题，下面是可展开的「原方案」全文；卡片表单不能上传图片，所以提示「要贴图/写长文直接回复这张卡」，
并留一个 `返回方案` 按钮（回调只带 `back`，不改方案），可以退回方案卡再看再点。输入框用单行（`input_type: text`），
手机上保持卡片内联，不跳成占满屏的多行文字编辑器；长文和贴图走「直接回复这张卡」。

卡片的文本兜底也保持决策简报（现象、修复锚点、影响面、预算，加一句「证据与完整方案在工单面板」）和
`回 1 通过 ｜ 回 2 换方向 ｜ 回 3 停`：客户端拒绝卡片时，问题仍然到得了人，分块按同样的要点行排版，长段不会糊成一片。

### 6.1.1 动态选项（worker 提问）

`orchestrator_plan` 可以带 `question`（一句话问题）和 `options`（2–4 个 `{ label, decision, note? }`）：`decision`
只能是 `approve` / `revise` / `stop`，选项只改变人看到的说法，不改变闸口的三种结果；带 `note` 的 `revise` 选项直接记录
这个方向，不带 `note` 的才展开表单。问题和选项随方案存档（`ticket.plan.question` / `ticket.plan.options`），被点的标签
记进 `plan.approved.option` 或 `plan.feedback[].option`，面板和归档能看到人选了什么。不传时仍是原来的三个按钮，旧卡片和
文本兜底不受影响；在聊天里直接回选项名与回 `1/2/3` 等效（intake 按标签精确匹配）。

同一张卡也能按语境换内容：`orchestrator_plan` 可带 `sections`（1–6 个 `{ label, text, fold? }`），按 worker 给的标题和正文排版，
`fold: true` 的块收进「补充」折叠；不传时仍是上面的八行标准布局。标准布局是**样式参考**：bug 修复、需求推进的方案卡按它来，
其他语境（评审、取舍、多方案对比等）用 `sections` 写当下真正要人看的几块，而不是硬套八行。`sections` 的正文同样按要点拆行，
URL 同样变成标题链接。方案正文（`plan.text`）仍按固定模板存，`missingPlanLabels` 校验不变；`sections` 只决定卡片正面与折叠里显示什么，文本兜底同步用同样的分块。

### 6.2 三个入口，一个决策态

| 入口 | 人的动作 | 落到哪 |
| --- | --- | --- |
| 飞书卡片 | 点 `通过` / `改一下` + 一句 / `停` | `card.action.trigger` → `engine.decidePlan(..., 'feishu')`，卡片原地替换成结果 |
| 面板工单页 | 同一个决策块，证据在面板里就地展开 | `POST tickets/:id/plan` → `engine.decidePlan(..., 'panel')` |
| 聊天里直接回 | 回 `1` / `2 换方向` / `3`，或直接回卡片上的选项名 | 当前唯一在等的方案 → `engine.decidePlan(..., 'session')` |

三个入口都**不产生 Trigger、Decision 或 Eval**，也不绕 worker 一轮；worker 只收到一条输入：
「人（飞书/面板/会话）通过了 P1 方案」或「换了方向：…」或「停了」。飞书私聊每条消息是独立话题，
所以裸 `1` 找不到订阅线程时，intake 会把它交给该发送者唯一在等的方案；同时有多张在等就保持歧义，不猜。

面板工单页的方案块把同样的材料排成可扫读的几块：先从**现象/修复锚点/影响面/预算**里抽出文件路径和行号，
列成「计划改动 N 个文件」的清单（只抽正面，证据里的行号仍留在折叠后）；每个文件行带着方案里提到它的那句说明，
点开是提到它的全部句子，避免只有文件名、看不到要改什么；每段再按 `；` / `。` 拆成要点，避免一整段糊在一起；
按钮上方另有一块「通过后」说明点了会发生什么（改几个文件、怎么验证、交付前不会 submit），
旁边一句写清 `改一下` 和 `停` 的去向。页头「打开 Session」旁的复制按钮复制 worker 的 Session id，方便在 DSH 里直接定位。
P1 时工单的工作区还没检出（`ticket.execution.directory` 为空或未 populate），所以这里给的是方案自己的说明，不是源码；
真实代码改动要等实现后在 Session 的「已编辑」卡里看（或后续把那张卡接进工单页）。

### 6.3 发送位置与卡片映射

方案卡发到**工单来源的那条飞书话题**：用工单 `channels` 里来源 feishu channel 的 `messageId` 发送
`im +messages-reply --message-id <来源消息> --reply-in-thread --msg-type interactive --content <json>`，带幂等键，
这样在话题里工作的人看得到、点得到；没有来源话题（例如非飞书来源的单）才退到 Source 配置里的「介入卡片私聊」，留空则发到工单来源的私聊，
用 `im +messages-send --msg-type interactive --content <json>`。发送成功后把
`message_id → { ticketId, planAt, url }` 记进 `KV.feishu.cards`（48 小时后清理）；回调没有工单号时靠它反查。
`url` 来自紧接着的 `im +messages-mget` 的 `message_app_link`（形如
`https://applink.feishu.cn/client/thread/open?…&thread_position=…`，`thread_position` 让它直接定位到这张卡）。
面板里只有卡片入口（「去飞书回答」）留在消息级链接上：卡片用发卡时记下的 `url`，没有卡片时退回来源消息或会话链接，
点开正好落到要回答的那张卡；工单页和话题页的「打开飞书原文」、话题 chip 则打开话题的**最新消息**：用同一话题链接去掉 `thread_position`
（会话链接去掉 `position`），只有会话链接时先用 `chatId` 和 `threadId`（话题 id，旧话题从首个 Trigger 的 meta 取）
补出话题链接，都拿不到才退回会话链接。过滤记录的来源链接仍指向被过滤的那条消息。链接按飞书的降级协议转成
`feishu://applink/client/…`（Lark 品牌为 `lark://applink/…`）后再放进面板：它直接拉起已安装的客户端，
不再先打开 `https://applink…` 的落地页，也就不会在浏览器里留下一个要手动关掉的标签页。
旧版本只存了会话链接的卡片和话题由 `linksLoop` 定期补齐（每轮最多 12 次 `im +messages-mget`，失败的下一轮重试），
部署后不用等新消息也能打开到具体消息。
方案已经被人从别的入口答过、或卡片对应的 `planAt` 已过期时，回调只把卡片替换成「已处理」，不再改工单。
只有工单的 actor 本人能点；别人的点击直接忽略。

### 6.4 运维前提

- 飞书开放平台 → 应用 → **事件与回调 → 回调配置**要启用；长连接模式不需要填 URL。
- `card.action.trigger` 由插件单独的 `event consume` 长连接消费，面板 Source 状态里对应 `飞书卡片按钮` 一项；
  没开回调时消费者能起来但收不到事件，不报错。
- 只有需要自动读取 `card_content` 时才要 `im:message:readonly`；本实现用 `message_id` 重建卡片，不需要该权限。
- 回调 token 30 分钟内、同一张卡片最多 2 次有效；过期就只记决策、不换卡片，不影响工单状态。

### 6.5 提问卡：worker 的 human_action 也带选项

worker 用 `orchestrator_report` 的 `human_action` + `options`（2–4 个短标签）提问时，主会话的 attention 回复不再只发
文本，而是发一张卡片：问题正文 + 每个选项一个回调按钮（`{ v: 1, attention: <attention id>, choice: <选项下标> }`），底下
写明「也可以直接在对话里回复」。卡片回复的 `message_id → { ticketId, attentionId, at, url }` 记进
`KV.feishu.attentionCards`（48 小时清理）；`url` 是这张卡自己的 `message_app_link`（`im +messages-mget`，查询失败只少这个
链接、不影响发卡），面板的「去飞书回答」用当前 attention 的这张卡定位问题；点击走 `engine.answerAttention`，把「人对「问题」选了：选项」作为这个人的
一条 Input 交给 worker（不是 bot note，不会被自动输入压住），并清掉 attention。问题已被回答、替换或卡片过期时，回调只
把卡片换成「已处理」，不改工单；仍然只有工单 actor 能点。飞书拒绝卡片时退回原来的纯文本回复。

提问卡同样接受 worker 的 `sections`（1–6 个 `{ label, text, fold? }`）：问题下面先排不分块，`fold: true` 的收进「补充」折叠，
仍然是问题 + 选项按钮 + 「也可以直接回复」。不传时保持原来的单行问题卡片；文本兜底把分块逐条写出。

提问卡只在真的需要点一下的关键节点上用，例如方案契合度确认、动手前的一次决定：`orchestrator_report` 只传 `human_action`
时仍走普通对话回复，只有同时传 `options`（2–4 个）才发卡片。日常提问用纯文本更快更轻，不要为了发卡而发卡。

3. TAPD 状态迁移白名单与「修复完成」分流
4. p4-iteration git 接进 P2
5. 预算与超时熔断（编译次数、总时长）
